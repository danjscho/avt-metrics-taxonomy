# v4.6 Phase 1 — Tier 1 threshold enumeration

Phase 1 of the threshold-numbers review (plan-future #8). Produces an exhaustive per-metric extraction of every numerical threshold / gate / baseline / formula in the 46 Tier 1 metric entries (= 42 distinct constructs + 4 sub-parts). For each threshold, records:

- **Threshold** — number / formula as written
- **Status** — `cited` (attributed to a specific catalogue handle / standard / paper that provides this number), `proposed` (explicitly Provenance-prefaced as taxonomy-proposed-as-starting-point), or `unflagged` (presented authoritatively without citation OR Provenance prelude)
- **Context** — what the number is for (alert / pause / baseline / pre-deployment gate / etc.)

This is **scoping only** — no metric content is changed. After review, Phase 2 will run a per-number verdict pass (keep / tighten / loosen / remove).

## Headline counts

- **46 Tier 1 metric entries** scanned
- **~150 distinct operational thresholds** enumerated
- **~12 cited** (mostly NAS Day Zero SPI, GDPR statutory, NHSE guidance)
- **~130 proposed** (taxonomy-proposed-as-starting-point with Provenance prelude)
- **~5 unflagged** (presented authoritatively without citation or Provenance prelude — small surface but the highest-priority review targets)

The dominant pattern: most Tier 1 thresholds are taxonomy-proposed and explicitly flagged as such. The honest-by-construction Provenance preludes do their job. The review surface for Phase 2 is therefore mostly about whether the *level* of the proposed numbers is right, not whether they're falsely cited.

## Tightening status reminder

Per the audit's tightening manifest (v4.5):

- **34 of 44 Tier 1 metrics tightened** with the Reference Standard / Operational Specification / Threshold Guidance pattern
- **10 not tightened**: GV.CR-3, GV.OP-5, GV.OP-6, GV.PD-9, GV.SG-9, GV.SG-11, GV.SG-13, GV.SG-17, TP.AC-5, TP.CC-6

The "not tightened" set has fewer thresholds (some have none — pure binary compliance — others carry numbers but without the structured pattern). Phase 2 / Phase 4 should consider whether these need pattern adoption.

## Cross-cutting observations

### Patterns worth noting before Phase 2

1. **The 0.1 / 0.5 / 1.0 severity-weighting formula is everywhere** (TP.ASR-12, TP.SN-5, TP.SN-6, TP.SN-15, TP.SN-20). It's a taxonomy-internal convention, not externally derived — and the same value lands in 5+ metrics' Threshold Guidance. Either it should become a single named convention (defined once, referenced by handle) or it should be re-examined as five independent calls.

2. **Tier-of-severity weighting is asymmetric for UMP_w only** (TP.SN-20) — the others use the symmetric 0.1/0.5/1.0. UMP_w's asymmetry is a deliberate choice because over-confidence (inflation) is more dangerous than under-confidence (deflation). Worth documenting that asymmetry rather than letting it sit as a one-off.

3. **The `≥ 200 test cases per EPR` floor recurs** in TP.WB-1, TP.WB-3, TP.WB-4 — it's the same recommendation across three closely-related metrics, which is fine but invites consolidation into a single test-set-design recommendation.

4. **Severity-1 / Severity-2 windows differ across metrics**:
   - GV.VT-5 incident disclosure: 24h / 72h / 7d / 30d
   - GV.SG-1 model-version notification: 24h / 7d / 14d
   - GV.VT-1 model-change notification (advance): 14d / 7d / 0d
   These all carry "proposed in v3.X" Provenance preludes but the fact that three metrics each pick different ladder values for similar-shape decisions invites a Phase 2 consolidation pass.

5. **Pre-deployment gates of 95 / 99 / 100 % cluster in the TP cluster** — the underlying decision (is `100 %` meaningful as a number, or is "zero-tolerance for safety-critical" the actual operational ask?) recurs across TP.ASR-13, TP.WB-1, TP.WB-3, TP.WB-4, TP.SN-5/6/15/20. Phase 2 could profitably ask: which of these should be `100 %` vs `≥ 99 %` vs "zero-defect on safety-critical only"?

### Status counts (rough)

- **Cited**: ~12 thresholds — primarily NAS Day Zero SPI (HL.HF-3a, HL.HF-3b, GV.OP-5, TP.SN-5 pause); UK GDPR statutory (GV.PD-10); v3.3 carried-from-prior on HL.HF-1 15-pp drop signal.
- **Proposed**: ~130 thresholds — the bulk; all carry honest Provenance preludes.
- **Unflagged**: 5 — TP.WB-2 IER < 0.001 ("standard SLA target"), GV.CR-3 100% labelling (zero-tolerance), GV.CR-6 100% all eight DCB0129 sections (structural), GV.SG-1 100% per-inference component-version coverage (structural), GV.TC-1 100% completion governance gate. **Of these, four are 100%-structural / zero-tolerance numbers where "unflagged" is actually defensible** (the number is the definition of compliance, not a threshold). **TP.WB-2 IER < 0.001 is the one genuine unflagged claim** — "standard SLA target" is a vague attribution; either tighten by citing where IER 1‰ comes from, or move to Provenance-prefaced proposed.

## Recommendations for Phase 2

The review surface is smaller than the raw threshold count suggests:

- **Most thresholds (~130)** are correctly Provenance-flagged as proposed — Phase 2 can verdict each as keep / reword / loosen / remove without needing fresh source-fetching
- **Cited thresholds (~12)** are already verified by the v4.2/v4.3/v4.4 Pass B sweeps — no Phase 2 work needed
- **Unflagged thresholds (5)** are the highest-priority Phase 2 candidates — only 1 (TP.WB-2 IER) needs new source-fetching; the other 4 are 100%-structural and just need a one-line clarification that 100% is definitional, not a proposed gate
- **Cross-metric consolidation candidates (4 patterns)** — the 0.1/0.5/1.0 severity-weighting, the 200-cases-per-EPR floor, the severity-window ladders, the 95/99/100 % cluster — are the highest-value Phase 2 unification work

Phase 2 (when scheduled) should expect to produce ~10–30 metric-content edits and zero new catalogue handles, plus the unification pass on the 4 cross-metric patterns.
