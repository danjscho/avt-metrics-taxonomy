# v4.6 Phase 2b — Cross-metric threshold consolidation

Phase 2a's verdict pass deferred ~20 thresholds to "Consolidate (Phase 2b)". This pass works through the 4 cross-metric patterns identified in Phase 1 and proposes a single consolidated decision for each. The output feeds v5.0 Threshold Reference page structure — these consolidations will become named cross-metric sections rather than buried per-metric rows.

The honest framing: when the same threshold (or near-identical threshold) recurs in 3-5 metrics, two things can be true. Either the underlying decision genuinely is the same and should be referenced once; or the decisions are independent and the apparent duplication reflects authoring habit, not deliberate framework. This pass tries to distinguish those cases.

---

## Pattern 1 — Severity-weighting formula `(0.1·benign + 0.5·moderate + 1.0·critical) / N`

**Recurs in:** TP.ASR-12, TP.SN-5, TP.SN-6, TP.SN-15. (TP.SN-20 uses an asymmetric variant for inflation; intentionally distinct.)

**The numbers (0.1 / 0.5 / 1.0)**: ratio of benign-class-impact to moderate to critical, ten-to-one and two-to-one respectively. Five-fold gap between benign and moderate, two-fold between moderate and critical.

**Author re-examination**: the pattern is doing one job — combining a multi-class error rate into a single severity-weighted scalar. The choice of weights *expresses a judgement about how much worse a critical error is than a benign one*. Five metrics independently picking 0.1 / 0.5 / 1.0 doesn't reflect five independent judgements; it reflects one judgement being copied across five metrics.

**Verdict — Consolidate as a named convention.**

- Define **"Standard symmetric severity weighting"** once, in the Threshold Reference page: `weighted_rate = (0.1·benign + 0.5·moderate + 1.0·critical) / N_total`.
- Each metric body keeps the weighted-aggregate definition (definitional to the metric — what is being measured) but cross-references the convention rather than restating the weights inline.
- Document the asymmetric UMP_w variant (TP.SN-20) as **"Asymmetric inflation-weighting"** — same shape, different semantics — and explicitly say *why* it differs.
- The convention is now consolidated; future metrics adding a multi-class rate cite the convention rather than minting their own weights.
- **Honest caveat to add:** the 0.1 / 0.5 / 1.0 ratio is author-judgement. There is no empirical anchor — a clinician-feedback round could plausibly argue for 0.05 / 0.5 / 1.0 (steeper benign-to-moderate gap) or 0.1 / 0.3 / 1.0 (shallower critical gap). The convention exists because *some* multi-class aggregation is needed; the specific weights are starting points.

## Pattern 2 — Test-corpus floor `≥ 200 cases per EPR / per category`

**Recurs in:** TP.WB-1, TP.WB-3, TP.WB-4 (with cell variant). Also adjacent: TP.ASR-13 (≥ 200 numeric tokens per sub-type), TP.SN-15 (≥ 200-sentence adversarial floor), TP.SN-20 (≥ 200 markers per cycle).

**The number (200)**: statistical floor for stable per-category rate estimation. Below this, confidence intervals on small percentages become uninformative.

**Author re-examination**: this is genuinely the same decision in every case. "How many test cases do you need before a per-category rate is statistically meaningful?" The 200 figure is rule-of-thumb-territory — for a 5 % event rate, 200 trials gives roughly ±3 % at 95 % confidence; for a 1 % event rate it's barely informative. The number is defensible but not derived from anything specific.

**Verdict — Consolidate as a named convention; tighten the framing.**

- Define **"Standard pre-deployment test-corpus floor"** once: `≥ 200 cases per per-category rate measurement, with the caveat that floors should be larger for rare-event rates (target: at least 10 expected events per category, which for sub-1 % rates pushes the floor above 1000)`.
- Each metric body cites the convention.
- **Important honest addition**: the convention should explicitly name the rare-event-rate caveat — for safety-critical 0 % zero-tolerance gates and < 1 % rates, 200 cases is insufficient. The current taxonomy uses 200 as a universal floor; the Threshold Reference page should say "200 is a floor, not a target — apply the rare-event-rate adjustment for any threshold below 5 %".
- This is the most honest acknowledgement the consolidation can produce: the 200 figure is currently being asked to do work it can't statistically support for tight thresholds.

**Cross-reference**: the ICC ≥ 0.85 inter-rater reliability convention recurs in TP.WB-1 / TP.WB-3 / TP.WB-4 as well. **Consolidate together** under "Standard pre-deployment test-corpus floor and inter-rater reliability convention" — they're paired in practice (you can't validate a test corpus without rater agreement on what counts as correct).

## Pattern 3 — Severity-window ladders for time-bounded decisions

**The metrics:**

| Metric | Decision | Ladder |
|---|---|---|
| GV.VT-5 Incident Disclosure | how-fast-must-vendor-disclose-by-severity | 24h / 72h / 7d / 30d (Critical / High / Med / Low) |
| GV.SG-1 Model Version Tracking | when-must-deployer-be-notified | 24h / 7d / 14d (median / alert / escalation) |
| GV.VT-1 Model Change Notification | how-far-in-advance-must-vendor-notify | 14d / 7d / 0d (Major / Moderate / Minor) |
| GV.VT-15 Retirement Notification | how-far-in-advance-for-retirement | 12mo / 6mo / 90d (Product / Feature / Integration) |

**Author re-examination — the most interesting consolidation candidate.**

These look superficially similar but they are *not* the same decision. They divide along two axes:

- **Direction of time**: GV.VT-5 (incident — *retroactive* disclosure window) vs the others (advance notification window). Inverse semantics.
- **Severity meaning**: GV.VT-5 severity is *of-the-incident*; GV.VT-1 is *of-the-change*; GV.SG-1 is *latency-since-event*; GV.VT-15 is *of-the-withdrawal-scope*.

Picking different ladders for these is in fact correct — they are not the same shape. But:

1. **The shape of the ladder is consistent across all four** — three or four severity bands, with each band roughly 3-7× the previous (24h → 72h ≈ 3×; 72h → 7d ≈ 2.3×; 7d → 30d ≈ 4.3×; 14d → 7d ≈ 0.5× *(this is the only inverse-ratio because it's an advance-notice ladder going from severe-needs-most-notice to minor-needs-least)*).
2. **The lowest bin in each is "immediate" / 0d / 24h** — meaning "don't wait" for the most-severe band.

**Verdict — partially consolidate.**

- Define **"Severity-band notification ladder convention"** — a meta-pattern, not a fixed ladder: severity-bands are 3 or 4; the most-severe band gets the most-stringent timing; ratios between bands cluster around 3-7×; the most-severe band is "immediate" (24h or less, or "before the change").
- Per-metric, retain the *specific* ladder values — they correctly differ because the decisions differ. But cross-reference the meta-pattern and document *why* each ladder picked its specific values.
- **Honest acknowledgement**: the v3.x author who picked 24h / 72h / 7d / 30d for GV.VT-5 was probably looking at HSE incident-classification timeframes; the v3.x author who picked 14d / 7d / 0d for GV.VT-1 was probably looking at vendor-change-control conventions. These are *different lineages*, both defensible, neither fully audit-traceable. Document the lineages where known.

## Pattern 4 — Pre-deployment percentage-gate cluster (95 / 99 / 100 %)

**Recurs across:** TP.ASR-13 (95 / 99 / 100 % per sub-type), TP.SN-5/-6/-15/-20 (95 % aggregate, 99 % continuous, 100 % critical), TP.WB-1/-3/-4 (95 / 99 / 100 % across pre-deployment / monthly / safety-critical). GV.CR-2 (95 / 90 / 85 / 75 ladder for survey).

**The pattern**: pre-deployment "must reach 100 % on safety-critical, ≥ 95 % overall, with a continuous-monitoring loosening to ≥ 99 %".

**Author re-examination — the most important consolidation question raised by the user direction.**

The user-direction conversation asked: *"should '100%' be the actual ask or 'zero-tolerance on safety-critical only'?"* This is the right question.

The cluster has two distinct semantic flavours:

1. **Aggregate-rate gates** (95 % aggregate, 99 % monthly continuous): these are *real* percentages — the metric measures a rate and the gate says "rate must be at least this".
2. **Definitional-zero gates** (100 % safety-critical, 100 % zero hallucinations): these are *category boundaries* — the gate says "no events in this class". 100 % on a binary "did all safety-critical fields write correctly" is just "zero failures on safety-critical".

The current taxonomy mixes these in the same Threshold Guidance blocks, which lets readers conflate them. A "100 % safety-critical fidelity" gate reads as "absurdly stringent percentage" when it is in fact "zero-tolerance category boundary" — same number, fundamentally different ask.

**Verdict — Consolidate by reframing, not by changing values.**

- Define two named patterns on the Threshold Reference page:
  - **"Aggregate-rate gate (95 / 99)"** — pre-deployment ≥ 95 %, continuous-monitoring ≥ 99 % loosening. Rates can drift; gates allow for that.
  - **"Zero-tolerance category boundary (100 %)"** — not a "threshold" but a category-membership rule. The gate is "no events in this class"; rendering it as 100 % is shorthand. Continuous-monitoring loosening from 100 % is not a 1 % loosening — it's "we accept that real-world drift will produce some events; the rate at which it does becomes its own metric".
- Per-metric, audit the existing `100 %` gates: which are zero-tolerance category boundaries (most of them) vs which are genuine 100 %-rate-targets (almost none — perhaps GV.CR-1 100 % dissent recorded, where the rate is the metric)?
- Re-render zero-tolerance gates as "zero-tolerance" in metric body prose; keep the 100 % numerical form on the Threshold Reference page with the framing column making the distinction explicit.

**This is the highest-value consolidation in Phase 2b.** It addresses the user's specific concern: if a deployer reads "must reach 100 %" they think it's a stringent percentage; they should be reading "no events in this class". The reframing doesn't change any number, but it changes how every safety-critical gate communicates.

## Summary of consolidation outputs

These four patterns become four named cross-metric sections on the v5.0 Threshold Reference page:

1. **Standard symmetric severity weighting** (with asymmetric variant) — single source of truth for the 0.1 / 0.5 / 1.0 weights, applied across 5 TP metrics
2. **Standard pre-deployment test-corpus floor and inter-rater convention** — applied across 6+ metrics, with explicit rare-event-rate caveat that the current taxonomy doesn't make
3. **Severity-band notification-ladder convention** — meta-pattern (3-4 bands, 3-7× ratios, immediate-most-severe), with per-metric ladders retained but cross-referenced
4. **Aggregate-rate gates vs zero-tolerance category boundaries** — the most important reframe; same numbers, fundamentally different communication

- **0 numerical values changed** by Phase 2b — all consolidations are reframings; the actual numbers stand
