# Tier 1 Definitional Rigour Classification (v3.3 audit, frozen at v3.4)

This is a research artefact recording the classification of every Tier 1 metric not yet tightened by v3.4, frozen at v3.4 ship date. It is the input to v3.5+ scoping.

## Methodology

For each Tier 1 metric not carrying the v3.3 tightening pattern (Reference Standard / Operational Specification / Threshold Guidance), the metric's Formal Definition was read against three criteria:

- Does it specify the **reference standard** (what counts as ground truth, with reliability where applicable)?
- Does it specify **operational decisions** (window, population, exclusions, mandatory breakdowns)?
- Does it specify **threshold or action** logic (gate, alert, pause)?

Classification:

- **TIGHT** — formal definition is operational; two competent measurers would compute the same value from the same data without further consultation. Tightening pattern would add structure without changing substance.
- **LOOSE** — formal definition uses unoperationalised terms or omits one or more of reference standard / window / population / threshold. Tightening pattern would surface concrete decisions currently implicit.
- **SURROGATE** — metric is a proxy for something else and the definition does not bound the proxy gap (e.g. a process metric standing in for a quality outcome).

### Cross-class observations

- **Compliance/governance metrics dominate the LOOSE bucket.** GV.CR-5/-6/-7, GV.PD-2/-8/-10/-11, GV.SG-11/-13/-14, GV.TC-1, GV.VT-1/-5/-7 — 14 of the 18 LOOSE entries. Tightening these is high-value because they are exactly the metrics a procurement officer reads first; their looseness is what makes "vendor-comparable evidence" a misnomer at procurement.
- **Pipeline metrics are mostly TIGHT or near-TIGHT.** TP.AC-5, TP.CC-6 are TIGHT; TP.ASR-12, TP.ASR-13, TP.WB-2/-3/-4, TP.SN-20 are LOOSE in narrow ways (specific test-corpus, severity-weighting, or per-EPR detail). Narrow pattern application possible.
- **Safety-governance metrics are heterogeneous.** GV.SG-9 and GV.SG-17 are TIGHT (the metric *is* the framework); GV.SG-11, GV.SG-13, GV.SG-14 are LOOSE. The tightening pattern fits some but not all.
- **Storage-location enumeration cascades.** Tightening GV.PD-1 in v3.3 implicitly raised the bar for GV.PD-2/-10/-11; explicit tightening would close the loop and make the dependency machine-readable.

## Suggested v3.5+ scoping

Three groupings emerge as natural waves:

**v3.5 Wave 1 — Compliance/governance core (8 metrics):** GV.CR-5, GV.CR-6, GV.CR-7, GV.TC-1, GV.VT-1, GV.VT-5, GV.VT-7, GV.SG-14. These are the procurement-first metrics where loose definitions have the highest practical cost. Pattern fits cleanly; provenance preludes will be Provenance-cited in most cases (DCB0129, NHSE IG, MHRA PMS).

**v3.5 Wave 2 — Privacy chain completion (4 metrics):** GV.PD-2, GV.PD-8, GV.PD-10, GV.PD-11. Closes the v3.3 storage-location enumeration loop; modest scope.

**v3.6+ — Pipeline narrow tightening (6 metrics):** TP.ASR-12, TP.ASR-13, TP.WB-2, TP.WB-3, TP.WB-4, TP.SN-20. Narrower pattern application — these are mostly TIGHT-ish with specific underspecified facets rather than wholesale loose. May be addressed via targeted Operational Specification additions rather than full pattern.

**Deferred / pattern-may-not-fit (5 metrics):** GV.OP-6, GV.SG-11, GV.SG-13, HL.HF-3, GV.SG-9. Each has a structural feature (LFPSE taxonomy gap, surrogate problem, the metric IS the threshold framework) that means the standard pattern is the wrong shape. Scope per-metric in v3.6+ rather than bundling.
