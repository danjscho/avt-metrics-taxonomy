# v4.3 verification scoping — extending Pass A / Pass B to remaining clusters

**Status:** scoping document, not yet a release plan. Reaction-stage; refine into `plan-v4.3.md` once scope and cadence are settled.

**Context.** v4.2 verified Formal Definitions + code snippets across the **TP cluster + IO.FE + ES.ME** subset (92 metrics) against cited sources. 18 metrics surfaced as 🔴 (confabulated source attributions). The remaining clusters are **GV (~81 metrics), HL (~21), PI (~21), IO.PX (~11) — about 134 metrics**. v4.3 is the candidate release for extending the same Pass A / Pass B methodology to those clusters.

The question this document is for: **is the v4.3 verification scope worth the effort, and what shape should it take?**

---

## The case for doing v4.3 verification

1. **The v4.2 methodology worked.** 18 🔴 surfaced from 92 metrics — not negligible. The Croxford bundle alone affected 6 metrics. If the same density of confabulation exists in the unverified 134, that's ~26 more 🔴s waiting to surface — same expected magnitude as v4.2.
2. **Pre-existing readers are at risk now.** v4.2's release notes and v4.2.1's link-up made the taxonomy more clickable and more cited. Confabulated source attributions in GV / HL / PI / IO.PX are now more likely to be quoted in procurement contracts, governance frameworks, and external commentary. The window for cleaning them up *before* they get baked into external references is narrower with each passing release.
3. **Audit-side ratchet.** v4.2 added the `check_crosscut_ref_ids_resolve` check. v4.3 verification would surface *catalogue-level* drift the audit can't catch alone — does the metric definition match the cited source? — which the audit can never fully automate. Doing it manually is the only path.

## The case against (or for narrower scope)

1. **Lower yield-per-hour expected.** GV is the largest unverified cluster but most GV citations point at *regulations / standards documents* (DCB0129, UK GDPR, NHSE IG Guidance, MHRA SaMD) rather than *papers with specific quantitative claims*. Regulations either say what they say or they don't — fewer "specific number wrongly attributed" patterns.
2. **HL and PI are construct-heavy, formula-light.** HL.HF metrics are workflow + human-factors constructs (edit rate, review-before-signing, automation bias). The citations point at qualitative-research literature where verification is "does this concept exist?" rather than "does this specific number match?". Different kind of work; different kind of failure mode.
3. **Diminishing-return shape.** v4.2's worst confabulations clustered in the most paper-citation-heavy cluster (TP.SN). The remaining clusters are progressively less paper-heavy. Most confabulated specific-number-attributions have probably already been caught.
4. **Substantial fixed cost per release** — plan-v4.3.md, triage tables, review files, cache structure, CHANGELOG, etc. The v4.2 release was ~5 working sessions even with the methodology bedded in. Worth weighing against alternative work (#4 Tier 1 review, #1 explorer, #8 thresholds review).

## Three options for scope

### Option A — Full extension (all 134 metrics)

Mirror v4.2 exactly, on the remaining clusters. Plan-v4.3.md, Pass A triage, Pass B source verification, Phase 3 fixes, Phase 4 code-snippet verification, Phase 5 release wrap. Estimated effort: **comparable to v4.2** (5–7 sessions), possibly less because the Pass B source bundle is smaller (regulations don't need fetching the way papers do — they're authoritative-by-name).

**Risk:** the bulk of effort goes into low-yield reading — verifying that GV citations point at the regulations they claim to point at. Most pass cleanly. Worth doing for completeness, but the marginal 🔴 yield is likely small.

### Option B — Surgical (high-yield slice only)

Limit v4.3 to the metrics most likely to harbour confabulations:
- **HL.HF (21 metrics)** — has paper-grounded constructs (PDSQI/PDQI for documentation review, automation bias literature). Some specific quantitative claims (review-before-signing rates, edit-rate distributions). Roughly TP.ASR-density of risk.
- **IO.PX (11 metrics)** — patient-experience metrics with cited literature (medication error rates pre/post-AVT, patient confidence surveys). Some quantitative claims worth verifying.
- **GV.SC (Security & Adversarial Robustness, 12 metrics)** — paper-cited research framework (prompt-injection literature, adversarial-ML benchmarks). Higher-than-typical-GV paper-citation density.
- **PI.E2E + PI.PP (21 metrics combined)** — composite end-to-end metrics with downstream-paper citations.

Skip the rest of GV (Privacy & Data Governance, NHS Compliance & Regulatory, Operational, Vendor Transparency, Training, Environmental) where citations are mostly to regulations.

**Total surgical scope: ~65 metrics.** Half the size of Option A. Expected 🔴 yield: similar absolute count, much higher per-hour rate.

### Option C — Audit-driven (no manual verification)

Don't do another full Pass B; instead **build out the audit to catch what manual verification caught in v4.2**. New checks:
- `check_specific_numbers_have_provenance_or_citation` — flag any specific quantitative claim (regex for `\d+(\.\d+)?%`, `F1 \d+`, `ICC \d+`, etc.) in a Formal Definition that isn't inside a ⚠ Provenance prelude or paired with a `[Handle]` citation.
- `check_acronyms_match_handle` — flag inline-defined acronyms (e.g. "SCRIBE = …") whose expansion doesn't match the catalogue handle's expansion.
- `check_cited_paper_dates_are_plausible` — surface citations that look like they're attributed to non-existent venues (e.g. "SPIE 2025" for clinical-AI work would be flagged for human review).

Each new check is a structural pattern, not a per-metric review. Cost: a release-sized engineering project but the work compounds — every future metric gets the protection automatically.

**Trade-off:** doesn't surface the 🔴s already in the unverified 134; only prevents new ones. v4.3 with Option C alone leaves the existing GV / HL / PI / IO.PX metrics unverified.

---

## Hybrid recommendation

**Option B + a slim version of Option C.**

Do the surgical Pass A / Pass B verification on HL.HF + IO.PX + GV.SC + PI (~65 metrics), get the most likely 🔴s out of the catalogue. Skip the rest of GV in the verification pass — accept that paper-citation density there is too low for the manual effort to be worth it.

**At the same time**, add 1–2 audit checks from Option C to ratchet the protection forward: specifically `check_specific_numbers_have_provenance_or_citation` is the highest-yield single check — it would have caught most of the v4.2 🔴s automatically, and it makes new metric authoring safer going forward.

**Defer:** the full GV verification pass and the more elaborate Option C audit checks (acronym matching, plausibility checking). Capture them as plan-future items.

## Out-of-scope decisions for this scoping (locked)

These belong elsewhere, not in v4.3 verification work:

- **Threshold-numbers review (plan-future #8).** Different kind of fix — design exploration about how the taxonomy *frames* threshold numbers, not whether they match a source. The v4.2 ⚠ Provenance preludes added during verification are inputs to #8, not outputs of v4.3.
- **Tier 1 gap review (plan-future #4).** Substantive content release in its own right; needs its own scoping.
- **ISO/BSI standards (plan-future #9).** Substantive new framework integration; should be its own release.
